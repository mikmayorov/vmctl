# vmctl

Набор команд для создания и управления ВМ на независимых хостах libvirt/KVM. Этот Git-репозиторий — точка входа для администратора: в нём находятся код, примеры конфигурации, инструкции, тесты и история изменений. Каждый хост получает собственную копию репозитория в `/opt/vmctl`; диски и установочные образы хранятся в выбранном локальном хранилище.

Для работы утилит достаточно Python 3.11+ из стандартной поставки: сторонних Python-пакетов нет. Системные утилиты и службы перечислены ниже. На странице проекта `vmctl` в вашем Git-сервисе скопируйте URL из кнопки **Clone**.

## Режимы работы

| Условие | Поведение |
| --- | --- |
| `netbox.key` или `NETBOX_TOKEN` задан | NetBox — источник истины. `vmctl` записывает желаемое состояние в NetBox **до** локального изменения. Если запись не удалась, libvirt не меняется. |
| Ключ отсутствует | Только локальное управление. Машины в NetBox не документируются. `audit`, `adopt` и `sync` недоступны. |

В управляемом режиме хост (`device`) создаётся **вручную** в NetBox и заранее привязывается к кластеру. В конфигурации vmctl указывается только `netbox.device` (имя или ID): кластер определяется по устройству, дублировать его в конфигурации не нужно. При ошибке локального действия запись NetBox остаётся; исправьте причину и повторите `sync` либо проверьте расхождение через `audit`.

## Установка из Git на новый хост

1. Подготовьте хост libvirt/KVM: установите Git, Python 3.11+, `virsh` и `qemu-img`; запустите службу libvirt и проверьте доступ к `qemu:///system`. Создайте каталог для дисков и сетевой мост. Для сценария cloud image установите `xorriso` и подготовьте образ с cloud-init. Названия пакетов и команды запуска службы зависят от дистрибутива.
2. Если нужен учёт в NetBox, **вручную** создайте там кластер и устройство этого хоста, затем назначьте устройство кластеру. Выдайте API-ключ с правами чтения устройства и чтения/создания/изменения виртуальных машин. При локальном режиме этот шаг не нужен.
3. На самом хосте клонируйте репозиторий в `/opt/vmctl`. Запускайте команды от пользователя, которому доступны каталог, libvirt и хранилище ВМ:

   ```bash
   git clone URL_ИЗ_КНОПКИ_CLONE /opt/vmctl
   cd /opt/vmctl
   cp config.example.toml config.toml
   chmod 600 config.toml
   ```

4. В `config.toml` укажите местные `host.libvirt_uri`, `storage.directory` и `network.bridge`. Для режима NetBox замените `netbox.url` и `netbox.device` адресом своего NetBox и точным именем или ID заранее созданного устройства; задайте `netbox.key` либо переменную окружения `NETBOX_TOKEN`. Переменная имеет приоритет над ключом в файле. Пустой ключ и отсутствие переменной означают локальный режим.
5. Запустите `python3 vmctl.py doctor` и устраните выявленные ошибки. При наличии ключа запустите `python3 vmctl.py audit`.
6. Если на хосте уже есть ВМ, просмотрите `python3 vmctl.py --dry-run adopt`, затем выполните `python3 vmctl.py adopt` и повторите `python3 vmctl.py audit`. `adopt` создаёт только отсутствующие записи ВМ и привязывает их к устройству хоста; локальные машины она не меняет. Повторный запуск пропускает уже учтённые ВМ. Совпадающее имя ВМ на другом устройстве того же кластера вызывает ошибку.

Каждый хост имеет собственные `config.toml` и `state/`. Эти файлы исключены из Git, поэтому обновление кода не заменяет местную конфигурацию и рабочее состояние. Не сохраняйте API-ключи или образы ВМ в репозитории.

## Обновление из Git

На каждом хосте обновляйте его рабочую копию отдельно:

```bash
cd /opt/vmctl
git status --short
git pull --ff-only
python3 vmctl.py doctor
```

Если нужна конкретная версия, используйте утверждённый тег или commit проекта при клонировании/обновлении и фиксируйте его в журнале изменений инфраструктуры. В репозитории доступны `vmctl.py` (CLI), `netbox.py` (API), `inventory.py` (чтение libvirt), `vmcreate.py` (создание ВМ), `config.example.toml`, `examples/` и `tests/`. Для локальной проверки исходников выполните `python3 -m unittest discover -s tests`.

## Разработка и публикация

Изменения разрабатываются в отдельной локальной ветке и проверяются на выделенном тестовом хосте. Конфигурация стенда, ключи, журналы и временные файлы хранятся только локально (`config.toml`, `state/`, `local/` исключены из Git). Общие примеры и инструкции должны оставаться независимыми от конкретного хоста.

Перед публикацией переносите проверенные изменения в основную ветку, запускайте `python3 -m unittest discover -s tests`, проверяйте `git diff --check` и просматривайте состав коммита через `git show --stat`. На Git-сервер отправляйте только основную ветку или утверждённый тег; локальные ветки разработки и стендовые файлы не публикуются. После проверки на реальном хосте отдельно фиксируйте, какая версия прошла испытание и что именно проверено. Пробные изменения на тестовом хосте не заменяют эту запись.

## Проверка и перенос учёта

```bash
python3 vmctl.py doctor
python3 vmctl.py audit
python3 vmctl.py --dry-run adopt
python3 vmctl.py adopt
python3 vmctl.py audit
```

`doctor` проверяет наличие локальных инструментов, доступ к libvirt, а при наличии ключа — доступ к устройству, его кластеру и списку ВМ в NetBox. `audit` сравнивает все локальные и привязанные к устройству записи NetBox: отсутствующие ВМ, CPU, память, суммарную ёмкость дисков, мост (если записан в контексте vmctl), питание и автозапуск. Возвращает код 1 при расхождении. Проверка читает данные и ничего не исправляет.

`adopt` переносит существующие ВМ в NetBox: имя, CPU, память, суммарную ёмкость дисков, состояние питания, автозапуск, мост и пути дисков. Источник установки для давно созданной ВМ неизвестен, поэтому он отмечается как `source = existing` в `local_context_data.vmctl`. Такую ВМ можно сверять и менять её питание; если она пропала локально, автоматическое пересоздание через `sync` невозможно. Сетевые интерфейсы и IP-адреса в NetBox этот первый вариант импорта не создаёт. При ошибке API ранее созданные записи остаются; после исправления повторите `adopt`.

## Команды ВМ

```bash
python3 vmctl.py check
python3 vmctl.py list
python3 vmctl.py info ИМЯ
python3 vmctl.py status ИМЯ
python3 vmctl.py pools
python3 vmctl.py networks
python3 vmctl.py start ИМЯ
python3 vmctl.py shutdown ИМЯ
python3 vmctl.py reboot ИМЯ
python3 vmctl.py autostart ИМЯ
python3 vmctl.py autostart-off ИМЯ
python3 vmctl.py console ИМЯ
python3 vmctl.py vnc ИМЯ
```

Команды просмотра читают локальное состояние. В управляемом режиме `start`, `shutdown`, `reboot` и изменение автозапуска сначала изменяют запись NetBox. `--dry-run` показывает действия без изменения NetBox и libvirt. VNC новых ВМ слушает `127.0.0.1` на хосте; для удалённого подключения используйте SSH-туннель.

## Создание ВМ

В TOML-файле запроса `[vm]` задайте `name`, `vcpus`, `memory_mb`, `disk_gb`, `source` и путь к установочному источнику. Примеры: `examples/ubuntu-iso.toml` и `examples/ubuntu-cloud.toml`. Замените пути к ISO, cloud image и данным cloud-init на реально существующие пути на хосте.

- `source = "iso"`: пустой qcow2-диск и установочный ISO (`iso = "/абсолютный/путь.iso"`).
- `source = "cloud_image"`: копия готового образа (`image = "/абсолютный/путь.img"`) и cloud-init (`user_data = "/абсолютный/путь"`). Перед запуском замените пример публичного SSH-ключа.

```bash
python3 vmctl.py --dry-run create examples/ubuntu-iso.toml
python3 vmctl.py create examples/ubuntu-iso.toml
python3 vmctl.py start example-ubuntu
python3 vmctl.py sync example-ubuntu
```

В управляемом режиме `create` создаёт в NetBox ВМ со статусом `planned`, читает сохранённые параметры и только затем определяет локальную ВМ. После успеха статус становится `staged`; запуск отдельный. Стандартные поля NetBox хранят имя, CPU, память, диск, устройство и кластер. Источник установки, пути, мост и каталог дисков записываются в `local_context_data.vmctl` этой ВМ. `sync` применяет сохранённые параметры NetBox и сверяет существующую ВМ. При отсутствии ключа `create` сразу создаёт ВМ локально и ничего не отправляет в NetBox.
